一、 手動設定テーブル詳細（インプット層とポリシー定義）

ServiceNow ITOM環境を構築する際、データのインプット源およびフィルタリングポリシーは、管理者が手動で維持する基準テーブルに完全に依存します。これらの事前設定テーブルが欠落している場合、水平および垂直発見エンジンは正常に動作しません。以下は、実務において手動設定が不可欠なコアテーブル一覧です：

1.1 Discovery（ディスカバリ）事前設定テーブル

テーブル名 (Table Name) ラベル名 (Label) 手動設定が必要な主要フィールドおよび業務用途
discovery_credentials Credentials 主要フィールド： type, user_name, password, key
用途： 対象OSにアクセスするためのSSH、WMI、SNMP、Windowsドメインアカウントなどの高権限認証情報を格納。
discovery_schedule Discovery Schedules 主要フィールド： discover, mid_server, run（実行頻度）, shazzam_batch_size
用途： スキャンスケジュールを定義。実行頻度、指定されたMID Server、および対象のIPレンジを動的に紐付けます。
discovery_range_item Discovery Range Items 主要フィールド： type(IP/Subnet), start_ip_address, end_ip_address
用途： MID Serverがプローブを発射する物理ネットワークの境界を手動で制限し、スキャン負荷が未承認領域に流出するのを防ぎます。
discovery_port_probe Port Probes 主要フィールド： port, protocol, scanner_class
用途： Shazzamフェーズで検出する開放ポートを制限。22(SSH)、135(WMI)、161(SNMP)等のスキャンポリシーを手動変更。
discovery_classy Discovery Classifications 主要フィールド： match_criteria, table_to_create, probes_to_trigger
用途： 分類器ルール。特定のポートが応答した際、対象システムがWindows、Linux、ルータのいずれであるかを判定。

1.2 Service Mapping（サービスマッピング）＆ Event Management（イベント管理）事前設定テーブル

テーブル名 (Table Name) ラベル名 (Label) 手動設定が必要な主要フィールドおよび業務用途
sa_m2m_service_entry_point Service Entry Points 主要フィールド： application_service, entry_point(URL/IPポート)
用途： 垂直トップダウンマッピングの起点。ビジネスサービスの「入り口」（例：本番環境Webサイトのロードバランサ仮想IPとポート）を手動で入力します。
em_connector_instance Connector Instances 主要フィールド： connector_definition(Zabbix/Prometheus等), host, credentials
用途： 外部監視システムとの標準統合インターフェースを手動設定し、イベントがServiceNowに流入するための技術パイプラインを確立。
em_event_rule Event Rules 主要フィールド： event_mapping, transform_compose, filter
用途： 非常に重要なデータクレンジングルール。未加工のテキストイベントを解析し、ホスト名や重要度を抽出して不要なノイズを排除するルールを手動構成。
em_binding_rule Alert Binding Rules 主要フィールド： ci_type, binding_strategy, match_attributes
用途： 手動ポリシー設定。生成されたアラート（Alert）を、CMDB上の対応するサーバまたはアプリケーションインスタンスのノードに正確に紐付ける条件を定義。

二、 自動生成・動的更新テーブル（CMDBアセット層）

前述の事前設定テーブルが整いスキャンが実行されると、MID Serverが収集したペイロードがバックエンドのIRE（識別・統合エンジン）を通過し、CMDB内にインクリメンタル（差分）として自動作成されるか、既存CIの属性が上書き更新されます。以下のテーブルは完全にシステムによって自動管理されます：

2.1 インフラストラクチャおよびミドルウェアのCIテーブル（自動作成/更新）

  • cmdb_ci_server（サーバ総合テーブル）： すべての物理マシン、仮想マシンのコアOS属性（ホスト名、ドメイン名、OSバージョン、製造シリアル番号など）を格納（子テーブルの cmdb_ci_win_server や cmdb_ci_linux_server へ派生）。
  • cmdb_ci_network_adapter（ネットワークアダプタテーブル）： ネットワークカードの一覧を動的に生成し、各物理ポートのMACアドレス、バインドされたIPアドレス、サブネットマスクをリアルタイムで更新します。
  • cmdb_ci_appl（アプリケーション・ミドルウェアテーブル）： パターン（Pattern）のディープスキャンにより自動生成されるコンポーネントレコード。自動取得・更新される Tomcat、MySQL、IIS などのソフトウェアインスタンスが含まれます。
  • cmdb_serial_number（デバイスシリアル番号テーブル）： 1台のホストにメインボード、シャーシ、BIOSなどの複数のシリアル番号が存在する場合、それらを自動的に紐付け、IREエンジンがデバイスの一意性を識別するための重要キーとして機能させます。

2.2 監視およびアラート実行時動的テーブル（実行時自動生成）

テーブル名 (Table Name) ラベル名 (Label) 自動生成・更新される動的な運用データの説明
em_event Events 外部監視ソースから絶え間なく送信される生の「イベントストリーム」。このテーブルはデータ量が非常に多くなるため、システムは定期的に古い履歴キャッシュを自動削除します。
em_alert Alerts イベントが em_event_rule によるフィルタリングを経て生成された正式な「アラート」。システムはこれを影響を受けるCMDBのアセットノードに自動関連付けします。
ecc_queue ECC Queue ITOM運用の非同期通信の心臓部。MID Serverへの指示（Output）と、MID Serverから返却されるスキャン結果（Input）が自動的に書き込まれます。
discovery_status Discovery Status スキャンスケジュールが実行されるたびに自動生成されるコントロールレコード。今回のスキャンで新規作成されたCI数、更新された旧CI数を記録します。

三、 内部テーブルの关联ロジック与リレーションシップ構築 (Relationships)

ServiceNow ITOMの真髄は、独立したアセット台帳だけでなく、これらの資産を自動的に紐付け、依存関係（血統網）を構築できる点にあります。以下の関連テーブルは、トポロジビューの核となる重要なデータ構造です：

3.1 物理・論理的リレーションシップテーブル：cmdb_rel_ci

CMDBにおける関係性のコアテーブルです。標準的な Parent ➡️ Type ➡️ Child の三元配置構造をベースに、アセット間の物理的・論理的依存関係を自動的に記録します：

  • Runs on :: Used by： 例：`Tomcat@discoverytest` (Child) が `discoverytest` Windowsサーバ (Parent) 上で Runs on（稼働）している関係。
  • Depends on :: Used by： ソフトウェアコンポーネント間の垂直方向のデータフローや依存関係。
  • Virtualizes :: Virtualized by： 物理ホスト（ESXiホスト等）と、その上で稼働する複数の仮想マシン（VM）間の仮想化ホスト関係。

3.2 ビジネスサービスと資産の関連付けテーブル：svc_ci_assoc

このテーブルは、Tag-Based Mapping および Top-Down Mapping の最終成果が格納される場所です。物理的な接続ではなく、「論理的な帰属関係」を格納します：
コアロジック： 具体的な物理CIのSys_IDを、抽象的なアプリケーションサービスレコード（cmdb_ci_service_discovered）に直接マッピングします。このテーブルにデータが存在することで、マップ表示画面に対象アセットが表示されるようになります。

四、 3大コアモジュールのライフサイクル実行プロセス

ITOMがシステム内でどのように「動的」に機能するかを解説するため、各モジュールの実行フローを直線的なステップで示します：

4.1 水平ディスカバリ実行フロー (Horizontal Discovery)

1. Scan (ポートスキャン)指示がecc_queueに書き込まれ、MID ServerがIPレンジを走査。22/135/161等の開放ポート状態を返却。
➔
2. Classify (デバイス分類)分類器の条件マッチング。135ポートが応答した場合Windowsと判定し、適切なWMI認証情報を割り当て。
➔
3. Identify (IRE識別)IREエンジンを呼び出しシリアル番号やMACアドレスを読み取り。既存CIがあれば更新、なければ新規作成を判定。
➔
4. Explore (詳細探索)詳細パターンプローブを実行。OS内部のネットワークアダプタ、ディスク、インストールソフト、Tomcatプロセス等をCMDBへ同期。

4.2 垂直サービスマッピング実行フロー (Service Mapping)

1. エントリポイント注入手動で sa_m2m_service_entry_point に技術的起点となるURL/IPを入力。
➔
2. ホストへのドリルダウンシステムがURLのIPルーティングを自動解析し、対象アプリケーションが稼働している物理/仮想ホストCIを特定。
➔
3. プロセス・通信依存の抽出sa_patternを起動しTomcatの設定ファイルを解析。接続先となるMySQLデータベースのIPとポートを自動抽出。
➔
4. トポロジの確定解析された垂直の依存関係をすべて cmdb_rel_ci に書き込み、サービス全体の依存関係マップを完成。

4.3 イベント管理のノイズ抑制とバインディングフロー (Event Management)

1. イベントの流入外部監視ツール（Zabbix等）の未加工アラートテキストがコネクタ経由で em_event テーブルに流入。
➔
2. ルール適用と降噪em_event_ruleにマッチ。重複する大量のノイズを統合・除外して em_alert テーブルに単一のアラートとして集約。
➔
3. CIノードへのバインドem_binding_ruleにマッチ。アラート内のホスト名情報から、CMDB上の対応するサーバノードを正確に特定して紐付け。
➔
4. サービスへの影響可視化対象サーバがバインドされたことで、Service Mapping経由で上位のビジネスサービスが即座に赤く点滅。障害のブラストラジアスを特定。

五、 特殊エッジケース：内部アクセス権限がない場合のCIデータ差異

データガバナンスにおいて頻発するエッジケースとして、対象ネットワーク上の特定のWindows PCに対し、MID Serverからのネットワーク疎通（Ping等）は可能であるものの、内部アクセス権限がない（WMI認証情報が誤っている、またはファイアウォールで135ポート等の管理ポートが遮断されている）シナリオがあります。この場合、ディスカバリはClassify段階で熔断（処理停止）されます。

🚨 認証情報・権限なし（熔断状態）におけるCMDBデータ差異の対照表：

👁️ 外部からの観測：システムが【取得可能な】基礎データ 🚫 アクセス拒否：システムが【取得不可能な】深度CIデータ
  • cmdb_ci_ip_address（IPアドレスCI）： 100%作成または更新されます。ネットワーク層での疎通が確認できるためです。
  • 開いているポートのアクティビティリスト： 135、445等の管理ポートが「Open」状態であるログ。
  • 大まかなハードウェアの空殻： 135ポートの応答から、システムは一時的に cmdb_ci_computer または Unclassed Hardware テーブルに、IPアドレスを名前にした空のレコード（例：10.10.1.55）を作成します。
  • 認証情報なしの指紋識別（任意）： Credential-less Discoveryが有効な場合、Nmapを利用して "Windows 10" や "Linux" 等のOS種別を推測しますが、あくまで推測の域を出ません。
  • cmdb_serial_number（製造シリアル番号）： ❌ 取得不可能です。BIOS情報を読み取るためのOS内部コマンドが実行できません。
  • 詳細なハードウェア構成： ❌ 取得不可能です。CPUコア数、ディスクパーティションサイズ（cmdb_ci_disk）、メモリ容量等は一切検知できません。
  • グローバルMACアドレス： ❌ 取得できません（対象デバイスがMID Serverと同一サブネットにあり、ARPブロードキャストで取得できる場合を除く）。
  • ミドルウェアおよびインストールパッケージ： ❌ 取得できません。レジストリやプロセスリストを読み取れないため、Tomcat等のノードは生成されず、Service Mappingはここで完全に断流（失敗）します。

六、 データの整合性とIREエンジンによるガバナンスのベストプラクティス

上記のような「認証情報なしの空殻アセット」がシリアル番号（Serial Number）やMACアドレスを持たない状態でCMDBに注入されると、運用上で深刻な問題を引き起こします。それが、大量の重複CI（Duplicates）の発生です。

重複発生のメカニズム： ServiceNowのバックエンドに位置するIRE（識別・統合エンジン）は、新規スキャンされたデバイスが既存アセットであるかを判断する際、第一優先としてシリアル番号、第二優先としてMACアドレスを照合します。これらが権限不足により取得できない場合、IREは最終的に最も信頼性の低い属性である IPアドレス でのマッチングを試みます。もし対象PCがDHCP環境にあり、翌日IPアドレスが変更された場合、IREはそれを「新しい別のコンピュータ」と誤認してCMDBに新たな空殻CIを作成してしまい、台帳が乱れる原因となります。

💡 このシナリオに対する技術ガバナンスのベストプラクティス：

  1. リモート・モバイル端末への対応： IPベースの無源ネットワークスキャンを廃止し、Agent Client Collector (ACC) メカニズムへ切り替えます。端末にACC軽量エージェントを導入することで、社内防火壁やネットワーク認証情報の制限を完全にバイパスし、端末側から能動的に完全なデータを安全に送信させます。
  2. クラウド上のシャドーITへの対応： IPスキャンを廃止し、標準の Cloud Discovery（API統合方式） を全面採用します。AzureやAWSの管理プレーンAPIから直接インベントリ情報とタグ（Tag）の情報を取得し、未承認の「ゴーストCI」の発生を源流で封じ込めます。
  3. 識別ルールの調整 (cmdb_identifier)： PCクラスや未分類ハードウェアクラスに対して独立したフィルタリングルールを設定し、シリアル番号とMACアドレスが同時に空である場合は、IREによるCMDB主表への書き込みを直接拒否して「要監査スタギング領域」へ隔離し、クリーンなCI環境を維持します。
